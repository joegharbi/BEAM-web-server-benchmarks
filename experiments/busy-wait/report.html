WSEB pilot · BEAM web servers · 1–2 October 2026

BEAM busy-waiting makes container energy unstable and inflated

In the pilot, several BEAM servers used up to four times more CPU from one run to the next for the same work, while the whole machine's energy stayed within 3%. A controlled experiment shows the cause: the BEAM schedulers' busy-waiting. Switching it off made the measurements stable and showed that most of the per-container energy was spinning, not work.

Laptop: Intel Core i7-10610U, 8 threads, 31 GB, Debian 13, kernel 6.12 · Scaphandre 1.0.3 (package 1.0.3-2) · Docker 29.8 · governor performance, turbo off, 1.8 GHz · on AC power

Setup

What was measured

  • Framework: WSEB, a controlled-measurement version (local branch, not yet published). Energy from Scaphandre's per-process power, summed over every process of the server's container and integrated over the load window.
  • Load: HTTP GET / from a Python client on the same machine, 100 parallel workers, kept-alive connections. Every server ran at about 800 requests per second, the client's limit, so all servers did the same work at the same rate.
  • Control: the minimal machine profile: fixed CPU frequency, turbo off, other containers stopped, screen at 1%, keyboard light, Wi-Fi and Bluetooth off, sleep blocked, charger required. Before every run the machine had to be back within 3 °C of its resting temperature with no throttling; every run passed.
  • Design: 5 repeats, each a full pass over all servers in a new random order (seed recorded), so slow drift spreads evenly.
Step 1 · Pilot

The observation: the machine was steady, some containers were not

11 static HTTP servers × 3 load levels × 5 repeats = 165 measurements, 6 h 27 min. At 80,000 requests the whole machine's energy varied by 0.4–2.7% between repeats. Container energy varied by up to 43% for some servers, while others were as steady as the machine.

Step 2 · Ruling out a measurement error

Two independent meters agree: the CPU use itself changed

  • Docker's own CPU statistics, which do not use Scaphandre, show the same jumps. Elixir Cowboy used 24% CPU in one run and 111% in another, both serving 80,000 requests in about 100 s.
  • Energy follows CPU time exactly: container energy per CPU-second is constant over all 110 measurements at 20k and 80k (0.108 J per CPU-%·s, CV 4%). Scaphandre assigns energy correctly; the server's CPU use varies.
  • The machine is not the cause: no throttling, every run started within the temperature limit, and the whole-machine energy varied by under 3%.

Hypothesis: BEAM scheduler busy-waiting. When a scheduler runs out of work, it keeps spinning on the CPU for a while before sleeping, so it can react faster to the next task. At a moderate request rate the schedulers often run out of work, and how much they spin can differ between runs. The rebar3 release template's own vm.args says: “Uncomment the following line if running in a container: +sbwt none”.

Step 3 · Controlled experiment

Switching busy-waiting off removes the jumps

Three of the unstable servers, each in two variants built from the same image: as it is, and with ERL_FLAGS="+sbwt none +sbwtdcpu none +sbwtdio none" (checked inside the running BEAM). 20,000 and 80,000 requests, 5 repeats, both variants mixed in one shuffled order: 60 measurements, 2 h 7 min.

Interpretation

What it means

  1. The cause is found. With busy-waiting off, the variation falls from up to 36% to at most 3.3%, so 5 repeats are enough again.
  2. Per-container energy counts spinning as work. Scaphandre shares the CPU package's power by CPU time. Spinning schedulers take CPU time, so the container is charged 2.9–6.7 times more energy for the same requests.
  3. The physical cost is smaller but real. The whole machine used 3.5–5.5% less energy with busy-waiting off, far beyond its 0.2–1.8% run-to-run noise. Container energy exaggerates the effect; both numbers belong in the paper.
  4. Servers become comparable. With the defaults the three servers were indistinguishable at about 210 J. With busy-waiting off they separate clearly: Elixir pure 31 J, Erlang Cowboy 44 J, Elixir Cowboy 61 J at 80,000 requests.
Limits

What this does not show yet

  • One request rate (about 800 per second, set by the client). At full load schedulers rarely run out of work, and the effect should shrink; the busy index servers were already stable.
  • Three servers, one laptop, static HTTP only. Dynamic and WebSocket servers are not tested yet.
  • The client runs on the same machine, so whole-machine energy includes it.
  • Container energy is an allocation by CPU time; network work done by the kernel and Docker's proxy is only in the whole-machine number.
  • A leftover test program (a stand-in for Scaphandre from a framework test, started the morning before) was found still running afterwards, so it ran during both measurements. It used little CPU: the machine's resting CPU use, measured at the start of both runs with it running, was 0.4–0.5%. It is not part of any container's energy, it added the same small amount to the whole-machine energy of every run, and in the experiment both variants ran mixed under the same conditions, so the comparison is unaffected. The framework now cleans up after an external stop, which is how it was left behind.
Next

Decision for the full campaign

Measure every BEAM server twice: with the default scheduler settings, as people run them, and with busy-waiting off. The framework will pass the setting to every container through one config line, so no Dockerfile changes and non-BEAM servers ignore it. Load levels start at 5,000 requests (1,000 requests lasts 1.3 s, only 1–2 power readings), and idle measurement is off (an idle server drew 0.1–2 mW; the machine at rest 2.7 W).

For the meeting

Talking order (about 10 minutes)

  1. The surprise (pilot chart): the machine is steady, some containers are not.
  2. Not our measurement: Docker's CPU statistics agree, and energy per CPU-second is constant.
  3. The hypothesis: busy-waiting, with the rebar3 template comment.
  4. The experiment (CPU and machine-energy charts): the jumps disappear, the machine saves 3.5–5.5%.
  5. The decision: campaign with both settings, and the limits we still have to test.

Likely questions

Could Scaphandre be wrong?
Docker's CPU statistics are independent of Scaphandre and show the same jumps, and the whole-machine energy agrees in direction.
Is 5 repeats enough for the p-value?
Every one of the 5 runs with busy-waiting off used less whole-machine energy than every default run, in all 6 comparisons; with 5 against 5 that is the strongest possible result (exact two-sided Mann-Whitney p = 0.008).
Is turning busy-waiting off fair to the BEAM?
It is a documented runtime option, suggested by the Erlang tooling itself for containers. The campaign measures both settings, so the default is still reported.
Does it hold at higher load?
Not tested yet: our client is limited to about 800 requests per second. The busy index servers were stable, which suggests the effect shrinks under full load.
